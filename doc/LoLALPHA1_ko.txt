================================================================================
LoL ALPHA1 — 구조와 언어 명세 (한국어판)
================================================================================

상태
--------------------------------------------------------------------------------

이 문서는 `doc/LoLALPHA1.txt`의 한국어판이다. 장과 절의 번호, 규칙 라벨, 문법,
코드는 영문판과 같다. 두 판은 함께 고친다. 두 판의 내용이 다르면 그것은
결함이고, 고쳐질 때까지는 영문판을 따른다.

LoL ALPHA1은 tactic이 없는 증명 스크립트 언어다. 이론은 `doc/LoLCore.txt`가
정하는 LoL Core다. 이 문서는 다음을 정한다.

  * 누가 무엇을 하는가 (0장)
  * 사용자가 무엇을 쓰는가 (1장, 2장, 4장)
  * 생략한 부분이 어떻게 채워지는가 (3장)
  * 커널 프로그램이 무엇이고 어떻게 실행되는가 (5장)
  * 결과를 어떻게 내보내고, 저장하고, 보고하고, 시험하는가 (6장부터 9장까지)

0장부터 9장까지는 규범이다. 10장과 부록 A는 참고다. 예제도 참고다.


================================================================================
0장. 부분과 경계
================================================================================

0.1 부분
--------------------------------------------------------------------------------

  위치                  언어        부분과 하는 일
  --------------------  ----------  --------------------------------------------
  src/Hol, src/X        Haskell, C  Hol 엔진. Hol 프로그램을 실행한다.
  lol/hol/kernel.hol    Hol         커널. LoL Core의 판단을 결정한다.
  lol/hol/elab.hol      Hol         elaborator. raw 항의 hole을 채운다.
  src/LoL               Haskell     호스트. 구문 처리, 엔진 구동, 저장,
                                    내보내기를 맡는다.

LoL은 람다 프롤로그로 작성된 커널 위에서 돌아가는 증명 보조기다. 커널과
elaborator는 Hol 프로그램이다. 호스트는 구문을 이리저리 옮길 뿐이다.

0.2 선언이 지나는 길
--------------------------------------------------------------------------------

  원문
      |   호스트: 어휘 분석, 구문 분석, 이름과 표기의 해석 (2장)
      v
  raw 항: `_`가 있을 수 있고 암시적 인자는 빠져 있다
      |   elaborator: hole을 전부 채운다 (3장)
      v
  Core 항: hole이 없다
      |   커널: ground 실행 (5장)
      v
  환경: 선언이 수락되어 들어간다

0.3 세 가지 실행
--------------------------------------------------------------------------------

  ground 실행
    커널이 hole 없는 선언을 검사한다. 무엇인가를 수락하는 실행은 이것뿐이다.

  elaboration 실행
    elaborator가 raw 항을 Core 항으로 바꾼다. hole은 Hol의 논리 변수이고, Hol의
    단일화가 그것을 채운다. elaborator는 아직 hole이 남아 있는 항에 대해 커널의
    환원 clause와 변환 clause를 부른다.

  대화형 실행
    elaboration 실행을 Hol 디버거 아래에서 하는 것이다. LoL BETA의 것이고,
    10장에서 미리 본다.

0.4 경계 규칙
--------------------------------------------------------------------------------

(B1) 수락. 선언은 커널의 ground 실행이 그 선언에 대해 성공한 뒤에만 환경에
들어간다(5.3절). 논리 변수나 잔여 제약이 들어 있는 답은 수락이 아니다. 자원
한도에 걸려 멈춘 실행도 수락이 아니다.

(B2) 호스트에는 의미가 없다. 호스트는 환원, 변환, 단일화를 구현하지 않고,
LoL Core의 어떤 규칙도 구현하지 않는다. 호스트가 하는 일은 어휘 분석, 구문 분석,
이름 해석, 항을 Hol 항으로 옮기기, 세션 구동, 선언 저장, 출력, 내보내기다.

(B3) elaborator는 제안만 한다. elaborator가 낸 항도 다른 항과 똑같이 (B1)을
거친다. elaborator에 결함이 있으면 옳은 스크립트가 실패할 수는 있다. 틀린
스크립트가 통과할 수는 없다.

(B4) 명시적 형식. 수락된 선언은 모두 명시적 형식(2.3절)으로 출력할 수 있다.
출력된 글을 다시 읽으면 elaborator를 돌리지 않고도 같은 Core 항이 나온다.
`LoL --explicit`가 파일을 이 형식으로 출력한다.

(B5) 고정된 범위. elaborator는 3장에 적힌 일만 한다. 하지 않는 일은 3.7절에
있다. elaboration 기능을 새로 넣는 것은 다음 버전의 명세를 바꾸는 일이지,
ALPHA1에 덧붙이는 일이 아니다.

(B6) 예산. 빈 줄과 주석을 뺀 줄 수로 세고, `test/lol/budget.sh`가 검사한다.

    1500줄 이하   lol/hol/kernel.hol
    800줄 이하    lol/hol/elab.hol
    6500줄 이하   src/LoL (생성된 렉서와 파서는 빼고 센다)

elaborator는 반드시 커널보다 작아야 한다.

(B7) 커널 방언. 커널은 Hol 가운데 5.4절이 정한 부분만 쓴다.

(B8) 신뢰. 믿는 것은 커널, Hol 엔진, 그리고 호스트 모듈 가운데 Core 항과 수락된
선언을 Hol 항과 사실(fact)로 바꾸는 것(`LoL.Hol.Embed`, `LoL.Env`)이다. 호스트의
나머지와 elaborator는 믿지 않는다.

(B9) 두 번째 의견. 수락된 선언은 모두 Rocq로 내보낸다(6장). 테스트 모음은
라이브러리의 모든 파일에 대해, 내보낸 결과를 Rocq로 컴파일한다.

0.5 누가 무엇을 결정하는가
--------------------------------------------------------------------------------

  커널이 결정한다.
    * 이 항은 타입이 맞는가?
    * 이 두 항은 변환 가능한가?
    * 이 재귀는 guard 조건을 지키는가?
    * 이 귀납 선언은 받아들일 수 있는가?

  elaborator가 결정한다.
    * 생략된 인자의 자리나 `_`의 자리에 무엇이 들어가는가?

  elaborator가 제안하고 커널이 결정한다.
    * 어느 인자가 struct 인자인가?

  호스트가 결정한다.
    * `x + y`는 무엇을 줄여 쓴 것인가? 여기의 `x`는 어느 `x`인가?


================================================================================
1장. 어휘 구조
================================================================================

공백은 토큰을 나눈다. 주석은 `(* ... *)`이고 중첩되지 않는다.

  ident     ::= (letter | '_') (letter | digit | '_' | ''')*
  qualid    ::= ident ('.' ident)*
  numeral   ::= digit+
  string    ::= '"' ('"'가 아닌 문자)* '"'
  operator  ::= symchar+
  symchar   ::= 다음 중 하나  ! # $ % & * + - / < = > ? ^ ~ \ | :

`_` 하나만으로는 `ident`가 아니다. 그것은 예약 기호다. `qualid` 안의 `.`
둘레에는 공백이 없다. 뒤에 공백이 오거나 파일이 끝나는 `.`은 명령을 끝낸다.

키워드:

  Arguments Axiom Check Compute Definition Fixpoint Import Inductive Infix
  Lemma Numerals Print Prop Set Theorem Type as end fix for forall fun in let
  match return struct with

다음 낱말은 키워드가 아니다. 보통의 식별자이고, 2.2절의 문법이 정해진 자리에서만
알아본다.

  Assumptions associativity at left level no right

구두점과 예약 기호:

  ( ) { } : := , . | => -> @ _ @{

예약 기호가 아닌 `operator`는 `Infix` 명령이 선언한 뒤에만 뜻을 가진다.


================================================================================
2장. 표면 구문
================================================================================

2.1 항
--------------------------------------------------------------------------------

  term    ::= 'forall' binders ',' term
            | 'fun' binders '=>' term
            | 'let' ident (':' term)? ':=' term 'in' term
            | 'match' term ('as' ident)? ('in' pattern)? ('return' term)?
              'with' branch* 'end'
            | 'fix' fixbody ('with' fixbody)* ('for' ident)?
            | term '->' term
            | term operator term
            | term atom+
            | atom

  atom    ::= qualid | '@' qualid | sort | numeral | '_'
            | '(' term ')' | '(' term ':' term ')'

  sort    ::= 'Prop' | 'Set' | 'Type' '@{' numeral '}'

  name    ::= ident | '_'
  binders ::= binder+ | name+ ':' term
  binder  ::= name
            | '(' name+ ':' term ')'
            | '{' name+ ':' term '}'

  branch  ::= '|' pattern '=>' term
  pattern ::= '@'? qualid name* | '_'

  fixbody ::= ident binder+ ('{' 'struct' ident '}')? ':' term ':=' term

적용은 모든 연산자보다 강하게 묶인다. `->`는 오른쪽 결합이고, 선언된 어떤
연산자보다도 약하게 묶인다. `forall`, `fun`, `let`, `fix`는 오른쪽으로 갈 수
있는 데까지 뻗는다.

2.2 명령
--------------------------------------------------------------------------------

  command ::= 'Definition' ident binder* ':' term ':=' term '.'
            | ('Theorem' | 'Lemma') ident binder* ':' term ':=' term '.'
            | 'Axiom' ident ':' term '.'
            | 'Inductive' indbody ('with' indbody)* '.'
            | 'Fixpoint' fixbody ('with' fixbody)* '.'
            | 'Arguments' qualid argspec+ '.'
            | 'Infix' string ':=' qualid
              '(' 'at' 'level' numeral (',' assoc)? ')' '.'
            | 'Numerals' qualid qualid '.'
            | 'Check' term '.'
            | 'Compute' term '.'
            | 'Print' qualid '.'
            | 'Print' 'Assumptions' qualid '.'
            | 'Import' qualid '.'

  indbody ::= ident binder* ':' term ':=' ('|' ident ':' term)*
  argspec ::= ident | '{' ident '}'
  assoc   ::= 'left' 'associativity' | 'right' 'associativity'
            | 'no' 'associativity'

2.3 명시적 형식
--------------------------------------------------------------------------------

항이 다음을 모두 만족하면 *명시적*이라고 한다.

  (X1) 항의 자리에 `_`가 없다. 숫자 리터럴과 연산자도 없다.
  (X2) 모든 바인더가 변수 하나를 묶고 타입을 가진다: `forall x : A, B`,
  `fun x : A => t`, 그리고 `fix`에서는 `(x : A)`.
  (X3) 암시적 인자가 있는 상수는 `@`를 붙여 쓰고, 그 인자를 전부 적는다.
  (X4) 모든 `match`에 `return` 절이 있다. 그 절이 scrutinee나 색인을 언급하면
  `as`와 `in`도 있다.
  (X5) 모든 `fix`와 `Fixpoint`에 `{struct x}`가 있다.
  (X6) 모든 패턴이 생성자의 매개변수마다 `_`를, 인자마다 변수를 준다. (X3)은
  패턴의 생성자에도 적용된다. 가지는 선언 순서대로 쓴다.

명시적 항은 Core 항 하나를 나타낸다. 3장의 어떤 규칙도 명시적 항에는 적용되지
않는다.

2.4 호스트가 항에 하는 일
--------------------------------------------------------------------------------

각 단계는 구문을 다시 쓰는 것이다. 어느 단계도 타입을 보지 않는다.

  [H-Name]     식별자는 묶인 변수나 전역 상수가 된다. 모르는 이름과 모호한
  이름은 오류다.
  [H-Arrow]    `A -> B`는 `forall _ : A, B`가 된다.
  [H-Binders]  바인더 묶음은 바인더 하나씩으로 쪼갠다.
  `forall (x y : A) (z : B), C`는
  `forall x : A, forall y : A, forall z : B, C`가 된다. `fun`도 같다. 명령의
  바인더는 타입 쪽에는 `forall`로, 본문 쪽에는 `fun`으로 들어간다.
  [H-Infix]    연산자는 선언된 level과 결합 방향에 따라 묶이고, 선언된 상수의
  적용이 된다.
  [H-Numeral]  숫자 리터럴 `n`은 `S (... (S O))`가 된다. `S`가 n번 적용되고,
  `O`와 `S`는 가장 최근의 `Numerals O S.`가 정한 상수다.
  [H-Fixpoint] `Fixpoint f ... := t.`는 `Definition f : F := fix f ... .`가
  된다. `Fixpoint ... with ...` 블록은 함수마다 정의 하나가 되고, 각 정의는 블록
  전체에 대한 `fix`다.
  [H-Position] 모든 노드는 원문에서의 위치를 지닌다.

그 결과가 3장이 받는 *raw 항*이다.

2.5 Rocq와 다른 점
--------------------------------------------------------------------------------

  * 우주. Rocq는 `Type`과 `Type@{u}`를 쓴다. ALPHA1은 `Type@{n}`만 쓰고 n은
  숫자다.
  * `Theorem`. Rocq에서는 증명 모드를 연다. ALPHA1에서는
  `Theorem c : A := t.`처럼 항으로 닫는다.
  * 주석. Rocq의 주석은 중첩된다. ALPHA1의 주석은 중첩되지 않는다.
  * 패턴. Rocq에는 중첩 패턴과 여러 scrutinee가 있다. ALPHA1에서는 패턴 하나가
  생성자 하나이고 scrutinee도 하나다.
  * 표기. Rocq의 `Notation`은 임의의 틀을 받는다. ALPHA1에는 `Infix`와
  `Numerals`만 있다.
  * `Arguments`. Rocq에는 옵션이 많다. ALPHA1에서는 암시적인지 아닌지만 정한다.
  * 모듈. Rocq에는 section, module, functor가 있다. ALPHA1에서는 파일 하나가
  모듈 하나이고 `Import`만 있다.
  * 귀납 원리. Rocq는 자동으로 만든다. ALPHA1은 만들지 않는다.


================================================================================
3장. hole 채우기
================================================================================

3.1 hole
--------------------------------------------------------------------------------

hole은 아직 알려지지 않은 Core 항을 나타내는 Hol 논리 변수다. elaborator는 다음
두 경우에 hole을 만든다.

  * 암시적 인자를 끼워 넣을 때마다 하나.
  * 항에 쓰인 `_`마다 하나.

hole은 단일화(3.5절)로만 풀린다. 명령 하나의 elaboration이 끝났을 때 모든 hole이
반드시 풀려 있어야 한다. 풀리지 않은 hole은, 그 hole이 만들어진 위치에서의 오류
`E-Unsolved`다. 기본값은 없고 일반화도 하지 않는다.

3.2 판단
--------------------------------------------------------------------------------

  G |- e => t : A       추론. raw 항 e가 타입 A의 t로 elaborate된다.
  G |- e <= A ~> t      검사. raw 항 e가 타입 A에 맞추어 t로 elaborate된다.
  G |- t =?= u          t와 u를 단일화한다.

G는 지역 문맥, 곧 지금까지 묶인 변수들과 그 타입이다. Hol에서는 `=>`로 넣은
가정들의 집합이다.

3.3 규칙
--------------------------------------------------------------------------------

[E-Const]  `@` 없이 쓴 상수는 앞쪽에 연달아 있는 암시적 인자마다 hole을 하나씩
받는다. `@`를 붙여 쓴 상수는 hole을 받지 않는다.

[E-App]  `h e1 ... en`에 대해:

  1. 머리 h를 elaborate하고 그 타입을 얻는다.
  2. 그 타입을 왼쪽부터 따라간다. 암시적 자리에서는 hole을 넣는다. 명시적
  자리에서는 쓰인 인자 가운데 다음 것을 가져와 그 자리의 정의역에 맞추어
  검사한다. 쓰인 `_`는 hole이다.
  3. 검사 모드에서는 그렇게 얻은 타입을 기대 타입과 단일화한다.

  쓰인 인자가 너무 많으면 오류 `E-Arity`다. 인자가 남았는데 머리의 타입이
  `forall`이 아니면 `E-NotFunction`이다.

[E-Lam]  검사 모드에서 `fun x => e`를, 약한 머리 정규형이 `forall x : A, B`인
타입에 맞출 때는 x : A를 두고 e를 B에 맞추어 elaborate한다. 바인더에 타입이 적혀
있으면 그 타입을 A와 단일화한다. 추론 모드에서는 타입을 반드시 적어야 하고,
없으면 오류 `E-NeedAnnotation`이다.

[E-Pi], [E-Let], [E-Annot]  구성 요소를 순서대로 elaborate한다. 타입이 올 자리에
온 항은 그 타입이 sort인지 검사한다. `(e : A)`는 e를 A에 맞추어 검사한다.

[E-Sort]  `Prop`, `Set`, `Type@{n}`은 자기 자신을 나타낸다. 레벨 없는 sort는
ALPHA1에 없다.

[E-Match]  `return` 절이 있으면 쓰인 그대로 쓴다. 없으면, 검사 모드에서 기대
타입이 T이고 scrutinee가 `t : I qs vs`일 때:

  * t와 vs의 원소가 전부 서로 다른 변수이면, P는 T를 그 변수들에 대해 추상한
  것이다.
  * 그렇지 않으면 P는 scrutinee와 색인에 의존하지 않고, T 그대로다.

  추론 모드에서 `return` 없는 `match`는 `E-NeedReturn`이다. 가지는 어떤 순서로
  써도 된다. 마지막 가지 `| _ => b`는 적지 않은 모든 생성자를 대신한다. 패턴은
  생성자의 이름을 적고, 그 생성자의 암시적이 아닌 자리마다 하나씩을 준다:
  매개변수 자리에는 `_`를, 인자 자리에는 변수나 `_`를 준다. `@`를 붙이면 모든
  자리에 하나씩을 준다. `in` 절의 패턴도 같은 방식으로 가족의 이름을 적고,
  색인마다 변수나 `_`를 준다.

[E-Fix]  `{struct x}`가 있으면 쓰인 그대로다. 없으면 elaborator는 타입이 귀납
가족인 인자들을 왼쪽부터 차례로 시도하고, 커널이 guard 조건을 받아들이는 첫
인자를 택한다.

[E-Switch]  검사 모드에서 위의 어떤 규칙도 맞지 않으면, `e => t : B`로 추론한
다음 B를 기대 타입과 단일화한다.

3.4 순서
--------------------------------------------------------------------------------

elaboration은 한 번 지나가는 것이고, 깊이 우선이며 왼쪽에서 오른쪽으로 간다.
미뤄 두는 것도 없고 다시 시도하는 것도 없다. [E-App]이 결과 타입을 비교하기 전에
쓰인 인자부터 검사하는 까닭이 이것이다. hole을 정해 주는 것은 쓰인 인자들이다.

실패하면 거기서 끝이다. 그 명령의 elaboration은 그 오류로 멈추고, 그 항을 달리
elaborate하는 방법을 더 시도하지 않는다. 되돌릴 것은 없다. elaboration 실행은
환경에서 출발해 자기 밖의 것을 바꾸지 않고, 환경은 ground 실행이 성공한 뒤에만
바뀐다(4장). 시도가 실패해도 elaboration이 계속되는 곳은 [E-Fix]의 후보들뿐이다.
실패한 시도가 묶어 놓은 것은 Hol의 백트래킹이 푼다.

3.5 단일화
--------------------------------------------------------------------------------

`G |- t =?= u`는 다음과 같이 결정한다.

  (U1) Hol의 단일화가 t와 u를 같게 만들면 단일화된 것이다. 이것으로 풀리는 것은
  두 가지다. hole과 항의 단일화, 그리고 서로 다른 묶인 변수들에 적용된 hole과 그
  변수들만 나타나는 항의 단일화. scope 검사와 occurs 검사는 Hol의 것이다.
  (U2) 그렇지 않고 t나 u가 hole이면 단일화는 실패한다.
  (U3) 그렇지 않으면 양쪽을 커널의 `whnf`로 약한 머리 정규형까지 줄인다. 머리가
  같으면 인자를 짝지어 단일화한다. 두 `forall`이나 두 `fun`의 몸체는 새 변수
  아래에서 단일화한다.
  (U4) 그렇지 않으면 단일화는 실패한다.

실패는 두 항을 담은 오류 `E-Unify`다.

3.6 elaboration 뒤
--------------------------------------------------------------------------------

elaborate된 선언에는 hole이 없다. 그 선언을 수락하거나 거부하는 것은 ground
실행이다(B1). 무엇이 타입에 맞는지에 대한 elaborator 자신의 판단은 그 결정에
관여하지 않는다.

3.7 elaborator가 하지 않는 일
--------------------------------------------------------------------------------

  ALPHA1에서 하는 것:
    * 암시적 인자, `_`
    * 1차 단일화와 패턴 단일화. 양쪽을 `whnf`로 줄여 가며 한다.
    * 단순한 `match`의 `return` 절
    * struct 인자. 후보를 하나씩 시도한다.

  ALPHA1에서 하지 않는 것:
    * 레벨 추론, 우주 다형성
    * 제약을 미뤄 두기, 백트래킹, 단일화 힌트
    * 중첩 패턴, 여러 scrutinee
    * section, coercion, type class

3.8 예
--------------------------------------------------------------------------------

`Arguments f_equal {A} {B} f {x} {y} e.`가 있고 `F p : eq nat (add p O) p`일 때,
`f_equal S (F p)`를 `eq nat (add (S p) O) (S p)`에 맞추어 elaborate한다.

  1. [E-Const]. `f_equal`은 앞쪽의 암시적 인자 둘에 hole을 받아
  `f_equal ?A ?B`가 된다.
  2. [E-App]. `S`를 `?A -> ?B`에 맞추어 검사한다. `?A := nat`, `?B := nat`.
  3. [E-App]. 다음 두 자리는 암시적이므로 hole `?x`, `?y`를 넣는다.
  4. [E-App]. `F p`를 `eq nat ?x ?y`에 맞추어 검사한다. `?x := add p O`,
  `?y := p`.
  5. [E-App]. 얻은 타입 `eq nat (S (add p O)) (S p)`를 기대 타입과 단일화한다.
  6. (U3). `add (S p) O`가 `S (add p O)`로 줄어들어 두 타입이 맞는다.

  출력은 `@f_equal nat nat S (add p O) p (F p)`다.

4장. 명령
================================================================================

  명령                  효과
  --------------------  --------------------------------------------------------
  Definition            타입과 본문을 elaborate하고 [D-Def]의 ground 실행을
                        한다. 투명하다.
  Theorem, Lemma        같되 [D-Thm]이다. 불투명하다.
  Axiom                 타입을 elaborate하고 [D-Ax]의 ground 실행을 한다.
  Inductive             매개변수, arity, 생성자 타입을 elaborate하고 [D-Ind]의
                        ground 실행을 한다.
  Fixpoint              [H-Fixpoint]를 거친 뒤 Definition과 같다.
  Arguments             상수의 어느 인자가 암시적인지 정한다.
  Infix, Numerals       그 파일의 나머지 부분과 그 파일을 import하는 파일에서
                        [H-Infix]와 [H-Numeral]을 확장한다.
  Check t               t를 elaborate하고 그 타입을 출력한다.
  Compute t             t를 elaborate하고 그 정규형을 출력한다.
  Print c               c의 선언을 명시적 형식으로 출력한다.
  Print Assumptions c   Assumptions(c)를 출력한다 (LoLCore 8장).
  Import M              모듈 M의 선언과 표기를 쓸 수 있게 한다.

선언의 바인더 `{x : A}`는 그 인자를 암시적으로 만든다. `Arguments`가 그것을
덮어쓴다.

실패한 명령은 아무것도 바꾸지 않는다. 선언, 표기, 인자의 암시적 여부가 그 명령
전과 같다.

5장. 커널 프로그램
================================================================================

5.1 Core 항을 Hol 항으로
--------------------------------------------------------------------------------

  kind tm type.
  kind lvl type.

  type lz    lvl.
  type ls    (lvl -> lvl).

  type prop  tm.
  type typ   (lvl -> tm).
  type cst   (nat -> tm).
  type ind   (nat -> nat -> tm).
  type con   (nat -> nat -> nat -> tm).
  type prod  (tm -> (tm -> tm) -> tm).
  type lam   (tm -> (tm -> tm) -> tm).
  type letin (tm -> tm -> (tm -> tm) -> tm).
  type app   (tm -> tm -> tm).
  type cas   (tm -> tm -> tm -> list tm -> tm).
  type fix   (nat -> list nat -> list tm -> ((nat -> tm) -> list tm) -> tm).

  cst N                 N번 상수
  ind B I               귀납 블록 B의 I번 가족
  con B I J             그 가족의 J번 생성자
  prod A (x\ B)         forall x : A, B
  lam A (x\ t)          fun x : A => t
  letin t A (x\ u)      let x := t : A in u
  cas (ind B I) P t Bs  match. P와 가지들은 함수다 (LoLCore 6장).
  fix K Ns Fs (f\ Ts)   함수 블록. Ns는 struct 인자의 위치들이고 Fs는
                        타입들이다. 본문 Ts 안에서 `f J`가 J번 함수다.

바인더는 Hol의 추상이다. 지역 변수는 `pi`로 들여온 상수다. 그 타입은 `=>`로 넣은
가정 `var_type x A`이고, `let`으로 묶인 변수에는 가정 `var_body x t`도 있다.
전역 이름은 번호다. 이름과 번호의 대응표는 호스트가 가진다.

레벨은 단항 표현이다. 그래서 레벨을 비교하는 데 산술이 필요 없다. Hol의 `=<`,
`+`와 Presburger 제약은 변수가 든 레벨 식을 위한 것이고, 그런 식은 LoL BETA에서
들어온다 (LoLCore 9장).

5.2 사실로 된 환경
--------------------------------------------------------------------------------

  cst_type N A.           모든 상수
  cst_body N T.           `Definition`만
  ind_type B I A.         가족의 타입. 매개변수를 포함한다.
  con_type B I J A.       생성자의 타입. 매개변수를 포함한다.
  ind_info B I ...        매개변수의 수, 제거 sort, 재귀 인자의 위치

호스트는 수락된 선언으로부터만 이 사실들을 만든다. `ind_info`의 내용은 커널이 그
블록을 수락할 때 계산한다. 호스트는 커널이 돌려준 것을 저장할 뿐이다.

실행 하나는 커널의 clause들과 한 환경의 사실을 본다. 그 환경의 선언 전부의
사실이고, 다른 선언의 사실은 없다. 호스트는 한 환경에 대한 실행들 사이에 그
사실들을 실어 둔 채로 두어도 되고, 검사할 선언이 의존하는 선언들의 사실만
실행에 주어도 된다. 커널은 상수를 번호로 조회하므로 어느 쪽이든 실행이 닿는
사실이 같고, 결과도 같다.

5.3 ground 실행
--------------------------------------------------------------------------------

  admit_ax A.               [D-Ax]
  admit_def A T.            [D-Def], [D-Thm]
  admit_ind Block Info.     [D-Ind]. Info는 출력이다.
  infer T A.                `Check`. A는 출력이다.
  norm T U.                 `Compute`. U는 출력이다.

  (R1) 질의에는 위에서 출력이라고 한 것 말고는 논리 변수가 없다.
  (R2) 첫 답이 답이다.
  (R3) 수락: 답이 있고, 그 답의 출력에 논리 변수가 없고, 잔여 제약이 없다.
  (R4) 거부: 답이 없다. 사유는 `expect`(5.5절)가 낸 첫 보고다.
  (R5) 미결: 엔진이 자원 한도나 오류로 멈췄다. 미결이라고 그대로 보고한다.
  수락도 아니고 거부도 아니다.

5.4 커널 방언
--------------------------------------------------------------------------------

  (K1) 모든 clause 앞에는 주석이 있다. 주석은 그 clause가 구현하는 LoLCore
  규칙의 이름을 적거나, 규칙 하나에 대응하지 않는 clause라면 무엇을 계산하는지를
  적는다. 주석 하나가 이어지는 clause 여럿을 맡아도 된다.
  (K2) 산술, Presburger 목표, `read`, `sigma`, `;`, `debug`를 쓰지 않는다.
  `print`는 `expect` 안에만 나온다.
  (K3) cut은 clause가 자기 경우임을 알아본 바로 뒤에만 나온다. 곧 머리 바로 뒤,
  `flex` 검사 바로 뒤, 또는 경우를 가르는 사실(`cst_body`, `var_body`)을 찾은
  바로 뒤다. 그 밖의 cut은 `expect`(5.5절)의 것 하나뿐이다.
  (K4) 항의 모양을 보는 술어는 모두, 그 항이 hole인 경우를 위한 `flex` clause로
  시작한다. `infer`와 `check`는 hole에서 실패한다. `whnf`는 hole을 그대로
  돌려준다. `conv`는 단일화한다. 부르는 쪽이 hole인 경우를 이미 걸러 낸 보조
  술어에는 그런 clause가 필요 없다.
  (K5) 지역 변수는 `pi`로 들여오고, 그 타입은 가정으로 준다.

ground 실행에서는 hole이 없으므로 `flex` clause가 하나도 발동하지 않는다. `flex`
clause가 있는 까닭은, elaborator가 hole 있는 항에 `whnf`와 `conv`를 부를 때
엔진이 후보 항을 나열하기 시작하지 않게 하려는 것이다.

`flex`는 Hol의 내장 술어다(HolBETA 3.6절). 인자의 머리가 묶이지 않은 논리 변수일
때 성립하고, 아무것도 묶지 않는다.

5.5 거부 사유의 보고
--------------------------------------------------------------------------------

  expect G E :- G, !.
  expect G E :- print E, fail.

실패할 수 있는 검사는 `expect Goal Report`의 꼴로 쓴다. 보고는 `rep L Ts` 꼴의
항이다. L은 대괄호를 뺀 규칙 라벨의 문자열이고, Ts는 관련된 항들의 리스트다.
전제 `E; G |- A : s`가 실패하면, 그 전제가 속한 규칙의 라벨로 보고한다. 호스트는
거부된 실행의 첫 보고를 진단으로 바꾼다(8장).

5.6 clause의 예
--------------------------------------------------------------------------------

  % (K4)
  infer M A :- flex M, !, fail.
  whnf M W :- flex M, !, W = M.

  % [T-App]
  infer (app M N) T :- !,
      infer M TM, whnf TM W,
      expect (W = prod A B) (rep "T-App" (M :: TM :: [])),
      check N A,
      T = B N.

  % [T-Lam]
  infer (lam A F) T :- !,
      sort_of "T-Lam" A _,
      (pi x\ var_type x A => infer (F x) (G x)),
      T = prod A G.

  % [T-Conv], `check`가 쓰는 꼴
  check M A :- infer M B, expect (sub B A) (rep "T-Conv" (M :: B :: A :: [])).

6장. Rocq로 내보내기
================================================================================

파일을 내보낸 결과는 `rocq compile -noinit`(Rocq 9.0)에 넣을 `.v` 파일이다.

  [R-Term]     모든 선언을 명시적 형식으로 출력한다.
  [R-Arrow]    `forall _ : A, B`는 그대로 출력한다. `-noinit`에서는 `->`를 쓸 수
  없다.
  [R-Sort]     `Type@{0}`은 `Set`으로 출력한다. n >= 1인 `Type@{n}`은
  `Type@{Ln}`으로 출력하고, 파일 머리에 `Universe L1 ... Lk.`,
  `Constraint Set < L1.`, `Constraint L1 < L2.` 등을 둔다.
  [R-Theorem]  `Theorem c : A := t.`는 `Definition c : A := t.`로 출력한다.
  [R-Name]     Rocq가 귀납형마다 만드는 이름(`I_rect`, `I_ind`, `I_rec`,
  `I_sind`)을 LoL 선언이 쓰고 있으면, 그 선언의 이름을 바꾸어 출력한다.
  [R-Import]   `Import M.`은 `Require Import M.`으로 출력한다.

테스트 모음이 검사하는 불변식: LoL이 파일을 수락하면, Rocq는 그 파일을 내보낸
결과를 컴파일한다.

7장. 파일과 모듈
================================================================================

원본 파일의 확장자는 `.lol`이다. 파일 하나가 모듈 하나다. 모듈의 이름은 프로젝트
루트에서 본 파일의 경로에서 구분자를 `.`으로 바꾼 것이다. `Import M.`은 M을 한
번만, 의존 순서대로 읽어 들인다. 순환은 오류다.

파일의 명령은 순서대로 처리한다. 처음으로 실패하는 명령에서 처리를 멈춘다.

오브젝트 파일의 확장자는 `.lolo`다. 버전이 적힌 텍스트 파일이고, 모듈의 선언마다
순서대로 이름, 종류, 명시적 Core 항으로 된 타입과 본문, 의존하는 이름들을
담는다. "이 선언은 검사되었다"는 표시는 담지 않는다. 오브젝트 파일은 그 파일의
모든 명령이 성공했을 때에만 쓴다.

  LoL --check-only F.lolo   F의 모든 선언에 대해 ground 실행을 한다.
                            프런트엔드와 elaborator는 쓰지 않는다.
  LoL --explicit F.lol      F를 명시적 형식으로 출력한다 (B4).

                        하는 테스트가 붙는다.
  test/lol/rocq.sh      pos/ 아래의 모든 파일과 라이브러리를 내보낸 결과를
                        컴파일한다.
  test/lol/budget.sh    (B6)을 검사한다. (B2)를 위해, src/LoL 아래에 `whnf`,
                        `conv`, `infer`, `check`, `unify`라는 이름이 없는지도
                        검사한다.

커널 테스트는 `test "name" :- goal.` 꼴의 clause이고, 그 앞줄에 `%! admit`이나
`%! reject L`이 있다. 커널 패치는 변이 파일(`.mut`)이다. `kernel.hol`에서 바꿀
줄, 바꾼 줄, 그리고 그때 반드시 기대와 어긋나야 하는 테스트(`kills`)나 반드시
수락되어야 하는 테스트(`admits`)를 적는다.

그 밖의 테스트는 `.lol` 파일과 사이드카 `.expected.txt`다. `test/smoke.sh`와
같은 방식이다. 음성 테스트는 실패했다는 사실만이 아니라, 보고된 라벨이나 코드를
확인한다. LoLCore의 규칙 라벨마다 pos/ 아래에 파일이 적어도 하나, neg/ 아래에
적어도 하나 있다. 모든 실행에는 시간 한도와 메모리 한도가 있다.


================================================================================
10장. 대화형 실행 미리 보기 (참고)
================================================================================

Hol의 디버거는 항을 대화식으로 짓기 위해 설계되었다. LoL BETA는 그것을 증명
모드로 쓴다. elaborator에 규칙이 하나 더해진다. 단일화가 풀지 못한 `_`는
`E-Unsolved`를 내는 대신 `debug`를 부른다.

  elab hole T M :- debug "goal", elab R T M.

그 지점에서 디버거는 지역 문맥과 목표를 sequent로 보여 주고, 사용자는 `_`의
자리에 들어갈 raw 항 R을 할당한다. R에 새 `_`가 있어도 된다. 그러면
elaboration은 R을 가지고 계속되고, 새 `_`마다 다시 멈춘다.

probe elaborator에서의 세션이다 (2026-11-11에 Hol BETA 인터프리터에서 실행했고,
엔진은 고치지 않았다).

  ?- elab hole (forall n : nat, add O n = n) M.

  [ |- elab R (forall n : nat, add O n = n) ?M ]
  R := fun n => _
    tactic `intro n`이 하는 단계다.

  [ n : nat |- elab R (add O n = n) (?M' n) ]
    여기까지 M := fun n => ?M' n 이다.
  R := eq_refl
    `apply eq_refl`에 해당한다. 암시적 인자는 3.3절의 규칙이 채운다.

  M := fun n : nat => @eq_refl nat (add O n)

여기서는 항을 표면 구문으로 보였다. probe는 Hol 항을 썼다. 마지막 항은 커널이
별도의 ground 실행으로 수락한다.

이것이 BETA에 주는 것:

  * 증명 상태는 멈춰 있는 세션이다. 목표를 위한 자료 구조를 따로 두지 않는다.
  * tactic은 R을 고르는 규칙이다. `exact t`는 t를, `intro x`는 `fun x => _`를,
  `apply f`는 `f _ ... _`를 준다.
  * 호스트는 단계마다 그 전에 세션의 snapshot을 찍는다. 단계가 실패하면 그
  snapshot으로 되돌린다. 증명 상태는 그 단계 전과 같고, 오류가 보고된다.
  snapshot이 없으면 틀린 R 하나가 증명을 끝낸다. 질의 전체가 실패하기 때문이다.
  되돌리기(Undo)는 더 앞의 snapshot으로 돌아가는 것이다.
  * `Qed`는 완성된 항에 대한 ground 실행이다. 그래서 tactic은 믿을 필요가 없다.
