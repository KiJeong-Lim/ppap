================================================================================
Hol BETA — Normative Language and Runtime Specification
================================================================================

Status
--------------------------------------------------------------------------------

This document is the complete specification of the Hol BETA dialect shipped by
`ppap`. It does not extend, and does not require the reader to possess, another
"base BETA" document. Chapters 0 through 8 and Chapter 10 are normative.
Chapter 9 is an informative map to the Haskell implementation.

The words MUST, MUST NOT, SHOULD, and MAY have their usual specification
meanings. When prose and an informative implementation note disagree, the
normative prose wins. A source location and a pretty-printed name are metadata;
neither changes kernel equality or proof-search results.

BETA is a simply typed, higher-order logic-programming language in the
lambda-Prolog family. Its defining runtime properties are:

  * depth-first, left-to-right proof search;
  * higher-order pattern unification with universe-level scope checks;
  * hereditary Harrop goals (`pi`, `sigma`, and local implication);
  * Prolog-style predicate-activation cut;
  * canonical-path modules with transitive, once-only imports;
  * multi-head clauses; and
  * natural-number arithmetic, Presburger constraints, and primitive I/O.


================================================================================
Chapter 0. Vocabulary and Conventions
================================================================================

0.1 Project and module vocabulary
--------------------------------------------------------------------------------

The *project root* is the canonical current working directory captured when a
main file starts loading. A *canonical path* is the filesystem's canonical,
absolute path after resolving relative components and symbolic links. A module's
identity is its canonical path, not an import spelling and not a header string.

An import declaration contains a *module locator*, such as `util` or
`stdlib.list`. Resolution maps a locator at one import site to a canonical path.
Two locators that resolve to the same canonical path denote the same module.

`ownEnv(M)` is the environment contributed by declarations physically present
in module `M`. It excludes built-ins and every imported declaration.
`exportEnv(M)` is the deterministic, once-only composition of the built-ins and
the `ownEnv`s in `M`'s transitive import closure, including `ownEnv(M)` itself.

0.2 Runtime vocabulary
--------------------------------------------------------------------------------

A *query activation* is execution of one top-level query. A *predicate
activation* is one invocation of a predicate, including all of the clauses and
local hypotheses considered for that invocation. A *choice point* is a saved
alternative branch. A *caller choice* was created before the current predicate
activation; a *right-hand choice* is created by a goal textually to the right of
an already executed cut.

A clause's free term variables are implicitly universally quantified and are
freshened on every clause invocation. A `sigma` variable is flexible; a `pi`
constant is rigid and belongs to a deeper universe level.

0.3 Order convention
--------------------------------------------------------------------------------

"Source order" means top to bottom within a file and left to right within a
conjunction or multi-head conclusion. "First" in search order means the branch
visited first by depth-first search. Unless stated otherwise, sequences in this
document preserve source order and are not sets.


================================================================================
Chapter 1. Source Language
================================================================================

1.1 Lexical forms
--------------------------------------------------------------------------------

Whitespace separates tokens. `%` begins a line comment. Block comments use
`(* ... *)`. Identifiers may be ordinary alphanumeric identifiers (with `_`),
quoted identifiers, or accepted symbolic identifiers. An unbound ordinary term
identifier beginning with an ASCII upper-case letter is a logic variable; an
ordinary lower-case identifier is a constant. A lambda binder shadows either
form.

The exact identifier spellings are:

  small-id      ::= [a-z] [A-Za-z0-9_]*
  large-id      ::= [A-Z] [A-Za-z0-9_]*
  quoted-id     ::= '`' small-id '`'
  symbol-start  ::= one of ! @ # $ ^ & * + - = < > ? / | ~ :
  symbol-rest   ::= symbol-start | '%'
  symbolic-id   ::= symbol-start symbol-rest*
  ident         ::= small-id | large-id | quoted-id | non-reserved-symbolic-id

Reserved words and reserved operator spellings are tokenized before `ident`.
Thus a reserved word is not an identifier merely because its characters match
`small-id`, and punctuation such as `+`, `:-`, or `=>` is not an `ident`.
Lexing uses maximal munch. In particular, `foo.bar.` contains the dotted module
token `foo.bar`, not two adjacent declarations `foo.` and `bar.`; separate such
declarations with whitespace.

Natural literals are non-negative decimal integers. Character and string
literals use Haskell-style single and double quotes, but the only accepted
escape spellings are `\n`, `\t`, `\\`, `\"`, and `\'`. An unescaped payload
character must be printable; other control characters and other Haskell escape
spellings (for example `\r` and `\NUL`) are lexical errors. A string denotes a
`list char`. `_` is a fresh wildcard at each occurrence. Lists use `[]`,
`[t1, ..., tn]`, and the right-associative constructor `::`.

A surface module name is:

  module-name    ::= simple-module-name
                   | module-segment ('.' module-segment)+
  module-segment ::= ASCII-letter (ASCII-letter | digit | '_')*

A `simple-module-name` is any single token classified by the lexer as an
ordinary `id`: a non-reserved ordinary identifier, a backtick-quoted lower-case
identifier, or a non-reserved symbolic identifier. Dotted names use the
stricter `module-segment` spelling shown above; quoted or symbolic segments are
not accepted inside a dotted name.

Module names occur only after `module` and `import`; they are locators or
path-derived display names, not term-level qualified names.

1.2 Programs and queries
--------------------------------------------------------------------------------

The top-level grammar is:

  program       ::= module-header? import-decl* declaration*
  module-header ::= 'module' module-name '.'
  import-decl   ::= 'import' module-name '.'

  declaration   ::= 'kind' ident kind-expr '.'
                  | 'type' ident type-expr '.'
                  | fixity-decl
                  | abbrev-decl
                  | notation-decl
                  | term '.'

  fixity-decl   ::= ('infixl' | 'infixr' | 'infix' | 'prefix')
                    operator precedence '.'
  abbrev-decl   ::= 'abbrev' ident ident* ':=' type-expr '.'
  notation-decl ::= 'notation' ident ident* ':=' term '.'
  query         ::= '?-' term '.'

`precedence` is an integer from 0 through 9. `infix` is non-associative.
Here `operator` is an `ident` or one of `+`, `-`, `*`, `/`, `=`, `=<`, `<`,
`>=`, `>`, `::`, `:-`, `;`, `=>`, `,`, `&`, `->`, `pi`, `sigma`, `s`, and
`is`. Other reserved words and punctuation cannot be named by a fixity
declaration.
The module header, when present, MUST be the first declaration. Imports MUST be
a contiguous block after the optional header. A later header or import is an
error. Repeating the same locator in one import block produces a warning and
has no additional effect. Repetition by a different spelling is collapsed if
both edges ultimately resolve to the same canonical path.

The REPL accepts queries, not module or import declarations. Loading a different
module is a load/reload operation rather than an interactive import mutation.

1.3 Kinds and types
--------------------------------------------------------------------------------

Kinds are generated by the first-order grammar
`K ::= type | type -> K` (with parentheses for grouping). In particular, every
arrow domain must be `type`; a higher-order domain such as the one in
`(type -> type) -> type` is rejected.

Types are generated by type variables, declared type constructors, application,
parentheses, and right-associative `->`. A type identifier beginning with an
upper-case letter is a type variable. Free type variables in a `type`
declaration are implicitly and simultaneously universally quantified. Their
source names and enumeration order do not change the scheme; every occurrence
still has one consistent binder identity. Every referenced type or data
constructor must be present in the composed declaration environment; kind and
type declarations are collected before facts are checked, so textual order
within those declaration classes is not a visibility rule.

The built-in and reserved surface kinds are:

  o      : type
  nat    : type
  char   : type
  list   : type -> type
  (->)   : type -> type -> type
  string : type                    (reserved direct type-constructor name)

The initial abbreviation maps `string` to `list char`. Like other
abbreviations, a module may shadow that default abbreviation in its own
expansion environment. The separate reserved kind entry prevents a direct
`kind string ...` type-constructor declaration; it does not prohibit
`abbrev string := ...`.

1.4 Terms, binders, and clauses
--------------------------------------------------------------------------------

Term application associates left. `X\ t` is lambda abstraction. Parentheses
override precedence. The principal built-in term forms and their types are:

  true, fail, !                 : o
  (&), (,), (;), (=>), (:-)    : o -> o -> o
  pi, sigma                    : (A -> o) -> o
  (=), is                      : A -> A -> o
  debug                        : string -> o
  [], (::)                     : list A; A -> list A -> list A
  s                            : nat -> nat
  =<, <, >=, >                 : nat -> nat -> o
  +, -, *, /                   : nat -> nat -> nat
  presburger                   : string -> o
  print, read                  : A -> o

A fact `h.` is a unit clause. `h :- b.` is a clause with conclusion `h` and
body `b`. A global clause conclusion must ultimately be an application of a
user-declared named predicate of type `o`, except that a conjunction conclusion
is a multi-head clause as specified in Chapter 3. Logical goals must have type
`o`. Section 3.3 separately permits supported arithmetic assumptions in the
antecedent of a local implication; that permission does not create global
arithmetic-headed program clauses.

1.5 Fixity and concrete conjunction spellings
--------------------------------------------------------------------------------

Application has precedence 10. The initial fixities are:

  prefix  Lambda 0       infixr :- 0       infixl ; 1
  infixr  => 2           infixl , 3        infixl & 3
  infixr  -> 4           infixr :: 4       prefix  pi 5
  prefix  sigma 5        infix   = 5        infix   =< 5
  infix   < 5            infix   >= 5       infix   > 5
  infix   is 5           infixl  + 6        infixl  - 6
  infixl  * 7            infixl  / 7

All fixity declarations in a module are collected before any term or notation
body in that module is resolved, so a declaration is module-wide regardless of
its textual position. Imported fixities are already in scope during this pass.

Comma and `&` are aliases for the same logical constructor, conjunction. A
fixity declaration for either spelling applies to both. They have identical
goal semantics and identical multi-head semantics. The canonical pretty-printer
spelling is `&`; comma remains accepted source syntax. In list syntax, commas
separate elements and are not goal conjunctions.

1.6 Abbreviations and notations
--------------------------------------------------------------------------------

`abbrev a X1 ... Xn := T.` defines a type-level read expansion. `notation n X1
... Xn := t.` defines a term-level read expansion. The declared parameters are
placeholders; expansion substitutes actual arguments capture-avoidingly.
Expansion happens before type checking and the kernel never treats an
abbreviation or notation name as definitional equality.

Parameter occurrences obey the ordinary variable syntax: type parameters occur
as upper-case type variables and term-notation parameters as upper-case logic
variables. A type abbreviation expands when it has at least its declared arity;
extra arguments are reapplied, while an under-applied type name remains
unexpanded. A term notation consumes its declared arity, reapplies extra
arguments, and eta-expands an under-application with lambdas for the missing
parameters. Expansion is recursive. A direct or indirect expansion cycle is a
compile-time error rather than an infinite rewrite.

The notation database also records inverse, presentation-only fold templates.
At user-facing write boundaries the pretty-printer MAY replace a matching
expanded term or type with the most recently applicable surface name. Folding
must not change the internal term and must not affect equality or search.

Within one module, a later abbreviation or notation with the same name shadows
an earlier one. Import composition and cross-module conflicts are specified in
Chapter 5.


================================================================================
Chapter 2. Static Semantics and Compilation
================================================================================

2.1 Declaration checking
--------------------------------------------------------------------------------

Kind and type environments are finite maps. Redeclaring an already visible kind
or data constant in the same composed environment is an error, except that two
imports may contribute an identical declaration as described in Chapter 5.
Built-in primitive data types (`nat`, `char`, and `list`) cannot be used as the
result head of a user data-constructor declaration.

Each clause is inferred and checked against `o`. Each query is independently
inferred and checked against `o` using the main module's `exportEnv`. Source
abbreviations and term notations are expanded before checking. Compilation then
introduces explicit type and term quantifiers for inferred free variables and
converts named binders to the kernel representation.

2.2 Multi-head shared typing
--------------------------------------------------------------------------------

If a top-level clause conclusion, or the conclusion of a clause used as a local
assumption, is a conjunction, flatten it left to right:

  h1 & h2 & ... & hn :- body.             (n >= 2)

The whole source clause is type-checked as one term with one free-variable map
and one type-unification state. Thus a variable name repeated in different
heads or in the body has one shared static type. The conclusion conjunction and
every `hi` have type `o`.

This shared checking is observably stricter than separately written clauses.
For example, if `p : nat -> o` and `q : char -> o`, then

  p X & q X.

is ill-typed. The two independent declarations `p X.` and `q X.` are each
well-typed because their `X`s belong to different clause scopes. Consequently,
a valid multi-head clause is not, in general, statically equivalent to blindly
copying its text into separate declarations.

Only after the shared type check succeeds may the fact installer/indexer split
the conclusion into searchable clauses; the compiled source clause may remain a
single conjunction until that point. Each indexed clause retains the common
typed body and the source order of its head. At runtime each clause is
instantiated separately, so logic variables, substitutions, residual
constraints, and cut activations are not shared between invocations. This
runtime independence does not undo the shared static typing rule.

2.3 Source locations during compilation
--------------------------------------------------------------------------------

Every surface `TermRep` node has an `SLoc`. An `SLoc` is exactly a begin and end
`(row, column)` pair, using one-based coordinates. It does not contain a module
name or file path; source identity travels separately in the compiler and
diagnostic context.

The compiler preserves locations on kernel constructors that support them.
Synthesized nodes MAY lack a location. Type errors SHOULD select the smallest
available surface subterm responsible for the error. Location metadata is
ignored by alpha-equivalence, beta reduction, unification, constraint solving,
fact indexing, and every other kernel decision.

Term-notation expansion rebases every node copied from the notation template to
the complete notation call-site span. A subtree substituted for a notation
parameter instead retains the subtree's original locations. Consequently, an
error in expansion-generated structure points to the use of the notation, while
an error inside an actual argument may point more precisely to that argument;
the template's declaration-site locations MUST NOT leak into diagnostics for a
later use.

2.4 Kernel index domain
--------------------------------------------------------------------------------

The semantic domain of a De Bruijn index is exactly the set of non-negative
integers. Constructing an index from a negative integer, evaluating or
otherwise semantically inspecting an internally forged negative index, and
passing a negative nesting count to the kernel's nested-lambda constructor are
deliberately `undefined`. A negative index is outside the term domain; it is not
an ill-formed term that an implementation may preserve or recover as an ordinary
error value.


================================================================================
Chapter 3. Logical and Search Semantics
================================================================================

3.1 Search order
--------------------------------------------------------------------------------

Proof search is depth-first and left-to-right. Global clauses are indexed by
predicate and tried in the once-composed clause order of `exportEnv`. Matching
global clauses are tried before matching local hypotheses. Local hypotheses are
tried in their installed order. A clause is freshly instantiated each time it
is tried.

For a predicate call, higher-order pattern unification matches the goal with a
candidate head. A successful match runs the candidate body and then the
remaining goals. Failed unification, an inconsistent constraint store, or
`fail` abandons that branch and resumes at the newest surviving choice point.

3.2 Primitive logical goals
--------------------------------------------------------------------------------

The logical forms have these operational meanings:

  true             succeed once without changing the proof state
  fail             fail the current branch
  G1 & G2          prove G1, then prove G2 with G1's resulting state
  G1, G2           exactly the same as G1 & G2
  G1 ; G2          try G1; on backtracking try G2
  F => G           install the clauses obtained from F, then prove G
  sigma X\ G       introduce a fresh flexible variable X, then prove G
  pi X\ G          introduce a fresh rigid constant at a deeper level, then G
  !                commit as specified in 3.4, then succeed
  debug "label"    enable interactive debugging, report the label, and succeed

Bindings must pass occurs and universe-level scope checks. A flexible variable
cannot be bound to a rigid constant or flexible variable introduced at a deeper
level.

3.3 Local implication and multi-head installation
--------------------------------------------------------------------------------

The antecedent `F` of `F => G` is an admissible local assumption or a
conjunction of admissible local assumptions. An atomic local clause may have a
user-declared named-predicate head or a predicate parameter already in scope
(for example one introduced by `pi`). A bare typed
equality is also admissible as a local equality hypothesis; when it is a
linear-natural equality, it additionally contributes an arithmetic premise.
The other supported arithmetic assumptions are bare `=<`, `<`, `>=`, `>`, and
installed `presburger` constraints. Equality, comparison, and Presburger
assumptions may occur under a universal `pi` prefix or conjunction, but none
may be the conclusion of `:-` with a body. Comparisons and Presburger
assumptions are solver premises, not callable predicate clauses. Logical
controls such as `true`, `fail`, `!`, `is`, disjunction, and a bare clause
constructor are executable goals, not admissible antecedent heads. Before
proving `G`, the runtime recursively expands
conjunctions in `F` and conjunctions in named-predicate clause conclusions.
For an arithmetic premise, a `pi` inside `F` quantifies the premise formula
itself: `(pi X\ A X) => G` has the shape `(forall X. A X) => G`, not
`forall X. (A X => G)`.
Quantifier prefixes and a shared body are copied onto each produced named head.
For example:

  (pi X\ (p X & q X :- r X)) => goal

installs, in this order, temporary equivalents of:

  pi X\ (p X :- r X)
  pi X\ (q X :- r X)

and then proves `goal` with that ordered block prepended to the pre-existing
local hypotheses. The expansion is simultaneous and left-to-right. It MUST NOT
be specified as the nested surface expression
`F1 => (F2 => (... => G))`, because repeated prepending would reverse the
search order of the produced hypotheses.

The installed user-named local clauses are scoped to `G`; they disappear when
that implication branch is left. Their invocation and cut behavior are
otherwise the same as global clauses. Local comparisons and Presburger
assumptions instead remain solver premises for the scope of `G` and are never
searched as predicate alternatives. A bare equality retains its ordinary local
equality-hypothesis behavior as well as any applicable natural-arithmetic role.
Every residual comparison or Presburger goal created in `G` captures the exact
arithmetic premise then in scope. That captured guard remains attached after
the implication cell is left; it is not reconstructed from whichever cell is
active during a later substitution or while printing the final answer.

3.4 Cut
--------------------------------------------------------------------------------

Cut has Prolog predicate-activation semantics. Executing `!` commits the current
predicate activation to all choices made since that activation began. It prunes:

  * the current predicate's remaining alternative clauses;
  * same-predicate sibling clauses produced by one multi-head declaration;
  * disjunction and other choice points created by goals to the left of the cut
    within that activation; and
  * equivalent alternatives from local hypotheses in that activation.

Cut does not prune caller choice points created before the current predicate
activation. It also does not prune choices first created by goals to the right
of the cut. A cut inside an imported clause behaves exactly like one inside a
main-file clause: a module boundary is not a cut barrier.

At top level there is no caller predicate. A cut executed directly by the query
therefore commits the current query activation. If execution later fails, no
pruned query alternative is reconsidered.

Splitting a multi-head declaration produces independent installed clauses, but
this is not a cut barrier. If two produced heads are alternatives for the same
predicate activation, a cut reached through the first commits past the sibling.
If they name different predicates, they can only be reached by distinct
predicate activations and no cross-predicate pruning follows.

3.5 Equality and higher-order unification
--------------------------------------------------------------------------------

`T = U` uses typed higher-order pattern unification. Beta-normalization and
scope-safe substitutions are kernel operations. Pattern disagreements that are
not yet decidable MAY remain as residual constraints; inconsistent
disagreements fail the branch. At every type, eligible bare equality hypotheses
have strict precedence over the built-in equality alternatives. If at least one
local hypothesis matches, only that ordered local branch block is returned and
enumerated; an identical or more general built-in answer is not appended. The
built-in equality path is used only when the local block is empty. At type
`nat`, arithmetic normalization is the first additional fallback; an undecided
equality then falls back to ordinary higher-order unification.
Consequently both `(1 = 2) => (1 = 2)` and its
normalized-source variant `(1 + 0 = 2) => (1 + 0 = 2)` succeed by reusing the
local hypothesis; the same equalities still contribute arithmetic premises to
other goals.

User names, display hints, notation folds, and `SLoc`s do not participate in
kernel equality.


================================================================================
Chapter 4. Arithmetic, Presburger Constraints, and I/O
================================================================================

4.1 Natural arithmetic and polymorphic `is`
--------------------------------------------------------------------------------

Natural literals and `s` denote non-negative integers. `+`, `-`, `*`, and `/`
have type `nat -> nat -> nat`. Evaluation of a ground expression is exact;
subtraction underflow and division by zero fail the branch.

`is` deliberately retains the polymorphic type `A -> A -> o`. Its behavior is
selected by the instantiated operand type and term shape. At `nat`, or whenever
an operand contains a natural-arithmetic constructor, `L is R` uses directional
arithmetic evaluation: the runtime evaluates or simplifies `R` before comparing
it with `L`:

  * a ground `R` is evaluated; a flexible-variable `L` may bind to that value,
    while a ground arithmetic `L` is evaluated and compared with it;
  * more generally, a flexible-variable `L` may bind to a simplified polynomial
    expression if occurs and scope checks pass;
  * an arithmetic equality decidable by evaluation or normalization is decided
    immediately; and
  * otherwise the goal leaves an evaluation constraint to be rechecked after
    later substitutions.

The symbolic `+`/`*` fragment is normalized as a polynomial. Thus
`20 * 20` normalizes to `400`, and
`C * (x + 1) = C * x + C` is recognized as an identity. A contradictory closed
arithmetic equality fails rather than becoming a residual constraint.

When neither operand has type `nat` and neither contains a natural-arithmetic
constructor, `is` normalizes both operands and submits their disagreement to the
same typed higher-order pattern unifier used by ordinary equality and clause
matching. Thus `X is 'a'` binds `X`, `'a' is 'a'` succeeds, and `'a' is 'b'`
fails. Occurs checks and universe-level scope checks still apply, and a
genuinely unresolved higher-order disagreement may remain as a residual
unification constraint. This non-arithmetic case is equality-like; only
arithmetic mode gives `is` its directional evaluation role.

4.2 Comparisons
--------------------------------------------------------------------------------

With no local arithmetic premise, `=<`, `<`, `>=`, and `>` decide ground
operands directly. Under a local implication, even a ground comparison is the
consequent of its captured premise; an inconsistent premise can therefore
discharge a false consequent. A non-ground comparison is accepted as a residual
constraint only when it can be translated to linear Presburger arithmetic.
Multiplication by a constant is linear;
`X * Y > 10` is not. An unsupported non-linear comparison is a runtime error,
not a silently retained opaque constraint.

Each retained comparison captures the local arithmetic assumptions in scope at
its creation and denotes a guarded lia-style implication. The runtime conjoins
all such guarded implications, then closes the conjunction once using the
quantifier order induced by logic-variable scope. Closing the whole store at
once makes one query variable denote one value across constraints even when
their captured guards differ. The runtime revalidates this closed conjunction
after relevant bindings and added constraints. Failure of that validity check
fails the branch. Entailed constraints may be omitted from the residual answer;
an unresolved guarded constraint is reported as `(premise) => consequent`.
Nested premises are captured and displayed in lexical outer-to-inner source
order.

4.3 `presburger`
--------------------------------------------------------------------------------

`presburger "formula"` parses the closed string during query or fact
installation and contributes the represented formula to the arithmetic store.
The literal must be available as a string at installation; a dynamic string
argument is not a Presburger source program. Free upper-case names in the
formula refer to same-named Hol logic variables in the installation context.

The formula language is:

  arithmetic atoms : non-negative decimals, upper-case/underscore variables,
                     parentheses, and `+`
  relations        : `=<`, `=`, `<`, `>=`, `>`
  congruence       : `t ==_{n} u`, where n is positive
  connectives      : `~`, `/\`, `\/`, `->`, `<->`
  quantifiers      : `forall X, f` and `exists X, f`
  false            : `_|_`

From weakest to strongest, connective precedence is `<->`/`->`, `\/`, `/\`,
then prefix `~`/quantification and atomic relations. Implication and equivalence
associate right; repeated disjunctions and conjunctions associate left.

Quantifier binding is lexical. A parse error is attributed to the actual Hol
string literal when that location is available. A retained formula succeeds
only while the conjunction of its captured premise implication and all earlier
guarded residuals is valid under the shared quantifier closure induced by
logic-variable scope. In particular, an inconsistent premise entails any
Presburger goal, as in ordinary implication.

4.4 `print`
--------------------------------------------------------------------------------

`print T` applies the current substitution, pretty-prints `T` using the active
module notation database and display-name cache, writes it, and succeeds without
changing the logical proof state.

Output is an external, irreversible effect. Backtracking does not retract a
line. If search re-enters the `print` goal, including after restoring a
snapshot, the line is printed again.

4.5 `read`
--------------------------------------------------------------------------------

Every execution of `read T` consumes exactly one REPL input line. The parser
uses the expected type when it is known:

  nat                 non-negative decimal natural
  char                one quoted character under the 1.1 escape policy
  string/list char    one quoted string under the 1.1 escape policy

Without one of those expected types it tries natural, then character, then
string. Parsing must consume the entire line. The five source escape spellings
and printable-character restriction from 1.1 apply here as well; in particular,
a host-Haskell escape outside that set is rejected. Invalid syntax or a
type/value mismatch fails the current branch, but the consumed line is not
returned to the input stream.

If `T` is one unbound flexible variable, the parsed value may bind it subject to
the usual occurs, type, and scope checks. If `T` is ground, `read T` succeeds
exactly when the normalized parsed value is structurally equal to it. A
partially-ground structured argument is not recursively unified by this
primitive and normally fails.

Backtracking or snapshot restoration does not restore input. Re-executing the
goal consumes another line.


================================================================================
Chapter 5. Modules
================================================================================

5.1 Canonical identity and path-derived names
--------------------------------------------------------------------------------

The loader canonicalizes the main path before reading it. That canonical path
is the main module's identity. Every successfully resolved import is likewise
canonicalized before cache lookup, cycle detection, duplicate elimination, or
composition.

Every loaded module MUST be inside the project root after canonicalization,
using filesystem path-component containment rather than a textual prefix test.
A main path outside the root is a load error. An import candidate (including a
symlink located under the root) whose canonical target is outside the root is
also a load error at its import declaration. The loader must perform this check
before admitting the path to its cache or graph.

For a canonical path under the project root, its path-derived name is the
root-relative path with the final `.hol` removed and path separators replaced
by dots. No case folding occurs. For example, canonical file
`<root>/lib/list.hol` has path-derived name `lib.list`.

An optional `module N.` header is an assertion, not a second identity. `N` MUST
equal the path-derived name exactly or loading fails. Headerless files retain
the path-derived display name. Because out-of-root modules are rejected, every
loaded file has a root-relative path-derived name.

5.2 Import resolution
--------------------------------------------------------------------------------

At `import a.b.c.` in canonical file `P`, replace dots by path separators and
append `.hol`, yielding `a/b/c.hol`. Test these candidates in order:

  1. the directory containing `P`; then
  2. the project root.

The first existing regular file wins and is canonicalized. If neither exists,
loading fails at the import declaration. Directory-first lookup permits
importer-local helpers. Therefore the locator string alone is not a globally
unique module name; only the resolved canonical path is identity.

Resolution is performed per edge. The resolved target path, not the locator
text, is retained in the import graph. A cache hit returns the already loaded
canonical module.

5.3 Deterministic once linearization
--------------------------------------------------------------------------------

For a root module `M`, compute `linearize(M)` with one global `visited` set and
one active recursion stack, both keyed by canonical path:

  visit(P):
    if P is active, report an import cycle;
    if P is visited, return;
    mark P active;
    visit each distinct direct import of P in source order;
    unmark P active; mark P visited; append P to the output.

The result is a depth-first, source-order postorder. Every canonical path occurs
exactly once, imports precede importers, and the main module is last. A diamond
such as `M -> A -> C` and `M -> B -> C` contributes `ownEnv(C)` once, at the
position of its first depth-first visit.

The built-in environment precedes the linearization. Formally:

  exportEnv(M) = fold compose builtins
                   [ ownEnv(P) | P <- linearize(M) ]

An implementation MAY cache parsed or elaborated modules, but it MUST NOT
construct this fold by concatenating already-transitive `exportEnv`s; doing so
would duplicate diamond dependencies. Cache, cycle, visited, and once keys are
canonical paths.

5.4 Environment components and declaration order
--------------------------------------------------------------------------------

`ownEnv(M)` contains only M's own kinds, type schemes, installed clauses,
fixities, type abbreviations, term notations, and warnings. `exportEnv(M)` makes
all composed declarations available transitively and unqualified.

Kind and type maps merge by name under the consistency rules in 5.5. Clause
sequences concatenate in linearization and source order; clauses never conflict
merely because their predicate names agree. Multi-head expansion preserves the
left-to-right head positions at the point of the source declaration.

Fixity, expansion, and presentation-fold databases are distinct components.
They are composed under the same once linearization but do not share an
underlying entry list. The final main-module databases govern interactive query
parsing and user-facing rendering.

5.5 Consistency and shadowing
--------------------------------------------------------------------------------

Two imported modules that contribute the same declaration name must agree as
follows:

  C1  kind declarations have structurally equal kinds;
  C2  type declarations have alpha-equivalent polymorphic type schemes, treating
      their quantified variables as one simultaneous binder set, so binder
      spelling and enumeration order are immaterial;
  C3  type abbreviations have the same arity and alpha-normalized parameter/body
      structure after discarding source locations and redundant parentheses;
  C4  term notations satisfy the analogous alpha-normalized structural check;
  C5  user fixities have the same associativity and precedence.

The equality in C3/C4 is deliberately structural and non-circular: normalize
formal parameter names to positions, normalize bound lambda names to binder
indices, ignore `SLoc` and parentheses, and compare constructors and
applications. It is not defined "modulo the notation database being merged".
A disagreement is a compile-time import inconsistency attributed to the later
import edge and should identify both origins when known.

Identical C1-C5 declarations collapse. Clauses concatenate rather than collapse.
Built-in fixities are defaults and may be overridden by a user module. A local
user fixity may not disagree with an imported user fixity. A module's own
abbreviation or notation may shadow an imported one; the shadow applies in that
module and is re-exported from it. Kind and data-constant declarations are
closed: a module may not redeclare an imported name even with a different local
intent.

5.6 Load failure and atomicity
--------------------------------------------------------------------------------

Lexing, parsing, resolution, cycles, inconsistent imports, kind/type errors,
notation installation errors, and Presburger installation errors abort the
load. No partially loaded environment becomes the active REPL program. Warnings,
including ignored duplicate imports, are emitted only for a successful load or
as otherwise explicitly reported by the loader.


================================================================================
Chapter 6. Source Locations and Diagnostics
================================================================================

6.1 `SLoc` contract
--------------------------------------------------------------------------------

`SLoc` is a metadata value containing inclusive begin and end positions:

  SLoc { begin = (row, column), end = (row, column) }

Rows and columns are one-based Unicode code-point positions; a horizontal tab
occupies one source column. Diagnostic caret indentation preserves preceding
tabs so the source and caret follow the same terminal tab stops. Coordinates
are not terminal-cell widths: exact visual alignment after East-Asian wide,
combining, or emoji code points is terminal-dependent and is not guaranteed.

It contains no path. The diagnostic call separately supplies an optional source
identity and source lines. Surface AST terms carry locations. In compiled
`TermNode`, `NCon`, `NApp`, `NLam`, and `NPresburgerCheck` may carry `Maybe
SLoc`; logic variables, de Bruijn indices, and suspensions do not themselves
carry a direct location. Compiler- or runtime-synthesized nodes may use
`Nothing`. Term-notation expansion follows the call-site/actual-argument
location rule in 2.3.

Reducers SHOULD preserve an existing useful annotation when reconstructing a
node. They are not required to invent a location for every result or to move an
application-site location onto a beta-reduced body. Diagnostics use the smallest
relevant available annotation and may be locationless when no sound annotation
exists. A fabricated `(0,0)-(0,0)` span is only a last-resort compatibility
fallback, not evidence of an actual source location.

Debug state rendering intentionally omits location metadata. This keeps the
proof-state view stable while retaining locations for errors.

6.2 Diagnostic rendering
--------------------------------------------------------------------------------

A located file diagnostic starts with a one-line GHC-like header:

  <canonical-path>:<line>:<column>-<end-line>:<end-column>: <severity>: [<tag>]

The renderer follows it with the source line and caret range when source text is
available. When a valid multiline `SLoc` is available but source lines are not,
it still renders every spanned row and a minimal caret: the first row starts at
the begin column, intermediate rows start at column one, and the last row marks
through the inclusive end column. File diagnostics use the canonical source
path, not a module header in square brackets. Interactive or truly locationless
errors may omit the source prefix and/or location.

`DiagnosticPretty` may use ANSI styling. `DiagnosticTest` removes ANSI escape
sequences while retaining the same words, coordinates, source excerpt, and
caret geometry so sidecar output is deterministic.

Lex and parse failures point to the failing token or EOF when available. The EOF
position is the cursor immediately after the last source code point; a final
newline therefore places EOF at column one of the following row. Module errors
point to the responsible header/import. Type errors point to the smallest
available offending subterm. For a term-notation use, 2.3 determines whether
that subterm has the call-site or actual-argument span. A Presburger parse error
points to its literal. Some runtime and HOPU failures have no trustworthy term
annotation and are therefore conformingly locationless; the specification does
not promise a location on every runtime error.


================================================================================
Chapter 7. REPL, Debugger, Snapshots, and Reload
================================================================================

7.1 Query lifecycle
--------------------------------------------------------------------------------

The REPL elaborates each query against the active main `exportEnv`, creates a
fresh search stack and query-variable type map, and enumerates answers in search
order. Query variables retain stable display names within the load generation.
When an answer has further alternatives, the REPL may ask whether to continue;
declining abandons the remaining stack.

At the top-level prompt:

  :q         leaves the current REPL
  :reload    reloads the current main file
  :d         toggles step debugging
  :short     selects abbreviated type display
  :verbose   selects expanded type display

During an active debug interaction, `:show ?X` inspects a displayed logic
variable and `:assign ?X := term.` proposes a scope- and type-checked binding.
Assignment failure is atomic. `:reload` is rejected while a query is searching
or at an in-query debug prompt.

Each displayed debug frame shows its pending goals/local hypotheses and call
identifiers, followed by the visible substitution, residual constraints, typing
context, and search-thread identifier. The remaining search stack follows the
current frame. `:short` shows the immediate folded type when known; `:verbose`
also renders the in-scope rigid/flexible context used to interpret generated
variables. Neither mode prints `SLoc` metadata.

7.2 Snapshot and restore
--------------------------------------------------------------------------------

A runtime snapshot records the logical search stack, pending debugger
substitution, and display-name cache state required to continue that search.
Restoring it is explicit logical time travel: the recorded stack replaces the
current stack. Consequently, restoring a snapshot taken before a cut resurrects
the alternatives that the later cut pruned. This does not weaken the cut rule;
restore deliberately moves execution to an earlier proof state.

The display-name cache is presentation metadata, not logical state. Restore may
merge it monotonically with names allocated after the snapshot so an already
shown name is not reassigned to another variable. Such retained mappings do not
retain a substitution, constraint, goal, or choice point from the later state.

Snapshot/restore covers logical runtime state only. It does not undo terminal
output, return consumed `read` input, retract other external I/O, or rewind the
global supply of implementation identifiers. Re-entered effects occur again.

A snapshot is valid only for the runtime instance and load generation that
created it. Reload invalidates all earlier snapshots; clients MUST NOT restore a
snapshot across reload. Implementations exposing snapshot values should enforce
or document this generation check rather than silently mixing environments.

7.3 Reload
--------------------------------------------------------------------------------

Top-level `:reload` starts a new load generation for the same requested main
file. It re-reads the file graph, re-resolves canonical imports, rebuilds loader
caches and composed environments, and creates new REPL debug, verbosity,
display-name, query-stack, and pending-substitution state. It is not an in-place
addition to the old environment.

Reload is not specified as operating-system process restart. Internal unique
identifier supplies may continue, and external effects remain visible. User
program meaning, module composition, diagnostics, and fresh REPL control state
must match a new load from the same filesystem state.


================================================================================
Chapter 8. Observable Compatibility Requirements
================================================================================

8.1 Determinism
--------------------------------------------------------------------------------

Given the same canonical project tree, query text, interactive responses, and
primitive input lines, module linearization, clause order, first answer, and
subsequent answer order are deterministic. Filesystem aliases must not duplicate
a module. Different canonical files reached through importer-local resolution
remain distinct even if their locators have the same spelling.

8.2 Existing programs
--------------------------------------------------------------------------------

BETA makes no blanket compatibility promise merely because a program is
headerless or uses only single-head clauses. Such programs still obey the exact
literal policy in 1.1, the local-assumption and equality rules in 3.3 and 3.5,
the polymorphic `is` and arithmetic rules in Chapter 4, and main-path root
containment in 5.1. Compatibility is therefore stated rule by rule: comma
remains accepted for conjunction, while presentation may intentionally differ
where BETA specifies canonical `&`, path-aware diagnostics, notation folding,
or explicit warning text.

The regression suite's `.expected.txt` files define exact CLI presentation
only where the test invokes the same diagnostic mode and canonical-path
normalization. They do not override the logical rules in this specification.

Chapter 9. Implementation Map (Informative)
================================================================================

9.1 Source organization
--------------------------------------------------------------------------------

The current implementation is under `src/Hol/BETA`:

  Header.hs          common kinds, types, logical operators, and `SLoc`
  Constant.hs        typed wrappers for runtime data/type constants
  PlanHolLexer.hs    tokens, surface AST, and source spans
  PlanHolParser.hs   programs, declarations, queries, and fixed core grammar
  FixityResolver.hs  module-wide user/imported fixity resolution
  ModuleLoader.hs    canonical resolution, graph loading, and composition
  Desugarer.hs       expansion and conversion from surface names/binders
  TypeChecker.hs     kinded type inference and checking
  Compiler.hs        explicit quantification and kernel conversion
  TermNode.hs        runtime term representation and reduction
  HOPU.hs            higher-order pattern unification
  Arith.hs           arithmetic and Presburger parsing/installation
  Runtime.hs         search, constraints, cut, debugger state, snapshots, I/O
  Notation.hs        fixity, expansion, and presentation folding databases
  Diagnostic.hs      tagged source/caret diagnostics and test rendering
  Debugger.hs        display-name cache helpers
  Main.hs            built-ins, CLI, REPL, primitive I/O, and reload loop

`src/Hol/Main.hs` dispatches the public Hol entry points to `Hol.BETA.Main`.

9.2 Current loader API
--------------------------------------------------------------------------------

`Hol.BETA.ModuleLoader` currently exports the record types `ModuleEnv(..)` and
`LoadedModule(..)`, plus:

  loadMain
    :: UniqueM m
    => KindEnv -> TypeEnv -> [TermNode] -> FilePath
    -> m (Either ErrMsg LoadedModule)

  loadMainWithDiagnostic
    :: UniqueM m
    => DiagnosticMode
    -> KindEnv -> TypeEnv -> [TermNode] -> FilePath
    -> m (Either ErrMsg LoadedModule)

  pathDerivedName :: FilePath -> FilePath -> String

  validateClauseTerm, validateLocalClauseTerm, validateGoalTerm
    :: TermNode -> Either TermNode ()

  polyTypeEq :: PolyType -> PolyType -> Bool

`ModuleEnv` exposes its path-derived name and canonical path, composed kind,
type, fact, notation, and expansion databases; separate own kind, type, fact,
notation, and expansion deltas; its canonical closure; direct import spellings
and their canonical target paths; and warnings. The three validators distinguish
global clauses, local clauses (including the arithmetic cases in 3.3), and
executable goals. `polyTypeEq` implements the C2 comparison. `LoadedModule`
exposes the composed main environment, the canonical-path-keyed loaded module
collection, the once-only load order, and warnings. These are Haskell
implementation interfaces, not stable Hol language syntax.

9.3 Runtime API status
--------------------------------------------------------------------------------

`Hol.BETA.Runtime` currently exposes its module contents, including
`RuntimeEnv`, `Snapshot`, `snapshot`, `restore`, and debugger commands. These
interfaces are internal integration surfaces. The semantic requirements in
Chapter 7 apply even if their Haskell representation changes.

The normative De Bruijn-index domain and failure policy are specified in 2.4.


================================================================================
Chapter 10. Required Conformance Cases
================================================================================

10.1 Module composition
--------------------------------------------------------------------------------

A conforming test suite must cover at least:

  M1  a headerless main module and an exactly matching explicit header;
  M2  a mismatched header at the header span;
  M3  importer-directory precedence over project-root resolution;
  M4  a missing import at its declaration;
  M5  a canonical-path cycle with the complete cycle chain;
  M6  a diamond in which a shared dependency's clause contributes once;
  M7  two locator spellings or symlink paths that canonicalize to one module;
  M8  distinct importer-local files with the same locator spelling remain
      distinct identities;
  M9  deterministic DFS source-order postorder and main-last composition;
  M10 identical and conflicting C1-C5 declarations, including both origins;
  M11 local abbreviation/notation shadowing and imported user-fixity rejection;
  M12 reload after an imported file changes, with no stale loader cache;
  M13 rejection of an out-of-root main path and an in-root symlink whose
      canonical import target escapes the root.

10.2 Multi-head and local assumptions
--------------------------------------------------------------------------------

Required cases are:

  H1  comma and `&` have identical goal and conclusion behavior;
  H2  head order is preserved after top-level splitting;
  H3  different heads receive independent runtime variables/constraints;
  H4  `p X & q X` is rejected when the two heads require incompatible types,
      while separately declared clauses type-check independently;
  H5  a shared binder and body are copied to every installed local head;
  H6  local multi-head hypotheses are searched left-to-right as one prepended
      block, without the reversal caused by naive nested implication;
  H7  comparison and Presburger premises beneath an antecedent-local `pi` are
      retained as universally quantified solver premises;
  H8  a residual arithmetic constraint keeps its originating premise after the
      local implication cell has been left and after later substitutions;
  H9  a bare nat equality is both a searchable local hypothesis and an
      arithmetic premise, including syntactically normalized equalities; its
      nonempty local match block suppresses built-in enumeration, while an
      empty block falls back normally.

10.3 Cut barrier matrix
--------------------------------------------------------------------------------

The suite must distinguish all of these cases:

  C1  `p :- !, fail.` prevents trying a later `p` clause;
  C2  a choice made to the left of cut in the same activation is pruned;
  C3  a disjunction first reached to the right of cut remains searchable;
  C4  a cut in a nested callee preserves an alternative in its caller;
  C5  a direct top-level cut commits the query activation;
  C6  caller disjunction remains available after a callee-local cut;
  C7  cut has the same barrier in a local-implication clause;
  C8  a cut through one same-predicate multi-head sibling prunes the other;
  C9  after post-cut failure in one different-predicate multi-head clause, its
      sibling remains reachable in the same caller search and uses a distinct
      activation;
  C10 importing the clause does not introduce a cut barrier;
  C11 restoring a pre-cut snapshot resurrects the recorded alternatives, while
      continuing without restore does not.

Each case must demand another answer or force post-cut failure where necessary;
merely accepting the first answer and declining enumeration does not prove that
alternatives were pruned.

10.4 I/O and snapshot effects
--------------------------------------------------------------------------------

Required cases are:

  I1  `print` observes the current substitution;
  I2  backtracking through `print` emits the line again and never erases output;
  I3  `read` parses known `nat`, `char`, and `string` types and uses the stated
      fallback order when no primitive expected type is known;
  I4  parse failure and ground mismatch consume the line and fail the branch;
  I5  backtracking re-executes `read` and consumes a new line;
  I6  a partially-ground structured `read` argument is not recursively unified;
  I7  restore rewinds logical state but not prior `print`/`read` effects;
  I8  a snapshot from an earlier load generation cannot be restored.

10.5 Locations, diagnostics, and arithmetic
--------------------------------------------------------------------------------

Required cases include multiline `SLoc` rendering both with and without source
lines, EOF cursor locations (including EOF after a final newline), canonical
file paths, color-free `DiagnosticTest` output, smallest-subterm type errors,
term-notation call-site rebasing with precise actual-argument locations, actual
Presburger-literal spans, a conforming locationless runtime error, polynomial
normalization, subtraction/division failure, linear residual comparison, and an
explicit unsupported-nonlinear runtime error. Conformance cases must directly
force the negative-index and negative nested-lambda cases from 2.4. Arithmetic
cases must also cover antecedent-local universal premises, guarded residual
display/rechecking, and the local-equality-before-arithmetic behavior specified
in 3.5.
